# Contributing

Спасибо за интерес к проекту. Изменения должны оставаться понятными, проверяемыми и совместимыми с официальным Zapret2.

## Перед началом

1. Проверьте существующие Issues и pull request'ы.
2. Для заметного изменения сначала создайте Issue с описанием проблемы и ожидаемого результата.
3. Создайте отдельную ветку от актуального `main`.
4. Не включайте в изменения `.hermes/`, `dist/`, `tools/preset-active.txt`, временные dry-run профили, токены, закрытые ключи и пользовательские данные.

## Требования к стратегиям

Новая или изменённая стратегия должна:

- использовать `winws2.exe` и актуальный синтаксис Zapret2, а не параметры Zapret1;
- загружать совместимые Lua-библиотеки;
- ссылаться только на файлы, присутствующие в репозитории;
- сохранять CRLF там, где этого требует Windows/Cygwin parser;
- иметь отдельный BAT-файл, если стратегия предназначена для ручного выбора;
- не обещать работу у всех провайдеров;
- содержать объяснение отличий от существующих профилей.

Если код или стратегия перенесены из другого проекта, укажите источник и лицензию. При необходимости обновите `NOTICE` и `LICENSES/`.

## Проверка

Перед pull request запустите из корня репозитория:

```bash
python tests/validate_project.py
python tests/validate_flowseal_alt_port.py
python tests/validate_strategy_variants.py
python tests/validate_release_zip.py
python tests/validate_security_metadata.py
python tests/validate_trust_docs.py
```

Для изменений профилей также выполните parser dry-run настоящим `winws2.exe`:

```bash
python tests/dry_run_profiles.py
```

Parser dry-run подтверждает синтаксис, пути и Lua-инициализацию. Он не подтверждает эффективность обхода у конкретного провайдера. В pull request отдельно укажите результаты фактической проверки, если она проводилась.

## Pull request

В описании pull request укажите:

- какую проблему решает изменение;
- какие файлы и стратегии затронуты;
- чем новая стратегия отличается от существующих;
- какие команды проверки выполнены и что они вернули;
- источник и лицензию стороннего кода или бинарников;
- известные ограничения.

Не прикладывайте пересобранные EXE, DLL или SYS без согласования происхождения, версии, лицензии и SHA-256. Не обновляйте bundled-компоненты случайными файлами из сторонних сборок.

## Стиль изменений

- Делайте небольшие тематические коммиты.
- Не выполняйте массовое форматирование вместе с функциональным исправлением.
- Сохраняйте существующие русские строки интерфейса и документации, если задача не связана с переводом.
- Обновляйте README и тесты одновременно с изменением поведения.

## Безопасность

Не публикуйте сведения об эксплуатируемой уязвимости в обычном Issue. Следуйте [`SECURITY.md`](SECURITY.md) и используйте private reporting.

Участие в проекте означает согласие с тем, что отправленный код может распространяться на условиях лицензии репозитория, а сторонние компоненты сохраняют собственные лицензии.
